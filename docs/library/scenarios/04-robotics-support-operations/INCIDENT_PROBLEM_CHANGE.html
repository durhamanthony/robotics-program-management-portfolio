Incident, Problem, and Change Management

Incident flow

Detect/report → establish safety state → identify customer/site/robot/version/entitlement → classify impact/severity → open correlation ID and incident roles → collect evidence → diagnose/restore → validate return to service → customer confirmation → review and link follow-up.

S1/S2 uses incident command with incident manager, technical lead, customer communications lead, safety/security/privacy leads as needed, field lead, and scribe. Preserve a timestamped decision/action timeline.

Problem management

Open a problem for repeat incidents, fleet/version clusters, material safety/security near misses, high cost, or unresolved root cause. Record known error, workaround boundaries, root cause, corrective/preventive actions, verification, affected population, release/field campaign, and effectiveness review.

Change/release

Every robot-affecting change has scope, affected serial/site/configuration, risk, test evidence, deployment rings, monitoring, maintenance/customer communication, approval, rollback and post-implementation review. Emergency change is faster, not undocumented. Case/problem/Jira/change/release/installed-product records share the correlation and version.

Closure criteria

Service is safely restored and verified; customer communication complete; evidence retained; follow-up owners/dates set; configuration updated; knowledge evaluated; and safety/security/reportability questions dispositioned by qualified owners.
